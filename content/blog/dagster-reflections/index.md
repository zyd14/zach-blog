## Op executions / asset materializations are expensive and slow
Op executions require instantiating a number of layered components internal to the Dagster framework, a number of which must yield events that need to be recorded synchronously by whatever event storage backend you're using. This can be slow considering it's all implemented in Python, which most people should know by now is pretty slow. If your event storage layer is remote, as is usually the case in production setups, then this will be even slower. I've worked with many practictioners on the Dagster Slack channel who are trying to get op initialization times minimized as much as possible, and it appears that initializations of under 5-10s can be quite difficult to achieve. Part of this is due to the fact that the primary [Executor](https://docs.dagster.io/deployment/executors) that gets used by most people is the [multiprocess_executor](https://docs.dagster.io/_apidocs/execution#dagster.multiprocess_executor), which spins up a new process for every op, requiring the OS to copy all the objects in memory to a new process (which can be quite expensive - this can be somewhat optimized with the scarcely-documented [forkserver option](https://docs.dagster.io/concepts/ops-jobs-graphs/job-execution#default-job-executor), but I haven't seen evidence that this option significantly improves startup times). There have been a significant number of [requests for a ThreadPoolExecutor](https://github.com/dagster-io/dagster/issues/4041) to attempt to address this startup penalty, but it appears the Dagster team [does not have it on their radar](https://dagster.slack.com/archives/C01U5LFUZJS/p1719928307029439?thread_ts=1719904935.167549&cid=C01U5LFUZJS), and there are no obvious OSS contributors taking it on.

## You're generally better off building your own IO managers and Resources

Dagster is a framework through-and-through, giving you the pieces you need to build a data pipeline in a very opinionated fashion with the goal of guiding you toward software-engineering best practices like dependency injection, separation of concerns, testability, and modularity. There have been a significant number of community contributions to create integrations with a myriad of services, but it's important to keep in mind that most of these integrations have a specific goal in mind which the integration was built to achieve. In other words, at least when it comes to IO managers and Resources that integrate with a specific service, often the integrations are not generalized to the point where they are flexible enough to serve all use cases.

There are certainly exceptions to this, but generally speaking, IO managers and Resources have pretty small footprints and are easy to build. By building your own you can not only tailor it to your needs, but you can remove dependencies on external libraries; maintain any Python project for long enough and you'll realize why this is a good thing. See the [broken state of python packaging](https://chriswarrick.com/blog/2024/01/15/python-packaging-one-year-later/).
